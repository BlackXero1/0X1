01 Executive Summary

Executive Summary

Modern malware increasingly executes without leaving a persistent disk artifact. Techniques such as process hollowing, reflective DLL loading, in-memory unpacking, and shellcode injection are designed to deny static analysis and reduce endpoint telemetry.

Across all five experiments, memory forensics recovered meaningful evidence in every case. Execution in memory leaves structural residue — VAD entries, PE headers, executable private regions, process relationships, network socket state, and decrypted strings — that persists until the process terminates or the system reboots.

In several scenarios this evidence survived deletion of the original on-disk artifact, making volatile memory the primary forensic surface.

02 Research Question & Hypothesis

When malware minimizes its disk footprint and reduces endpoint telemetry, what evidence remains in volatile memory — and how reliably can an analyst reconstruct the malicious activity from a Windows memory image alone?

This question decomposes into four sub-questions evaluated across each experiment:

  • Can the malicious process or injected region be identified?
  • Can the payload (code, PE, shellcode) be extracted?
  • Can runtime configuration and C2 information be recovered?
  • Does evidence survive deletion of the original disk artifact?

Hypothesis

Even when malware uses process injection, memory-only execution, in-memory unpacking, or deletion of disk artifacts, execution leaves residual structures in volatile memory that can be recovered through memory forensics and correlated with endpoint telemetry.

The hypothesis predicts that each technique will leave at least one category of recoverable evidence, and that the combination of Volatility 3 analysis, PE-sieve scanning, and endpoint telemetry (Sysmon, Procmon) will yield sufficient evidence to reconstruct attacker intent and capability.

05 Methodology & Evidence Collection

Experimental Protocol

Each experiment follows the same structured protocol to enable direct comparison:

  1. Baseline snapshot — take a clean VM snapshot and acquire a baseline memory image
  2. Deploy telemetry — verify Sysmon is running; start Procmon and Wireshark capture
  3. Execute sample — run or simulate the target technique in a controlled manner
  4. Timed captures — acquire memory images at T0 baseline, T1 during execution, T2 after activity, T3 after disk artifact removal where applicable
  5. Acquire endpoint telemetry — export Sysmon EVTX, Procmon PML, Wireshark PCAP
  6. Memory analysis — run the standard Volatility 3 plugin sequence against each image
  7. Payload extraction — dump suspicious regions and analyze with PE-bear and IDA Free
  8. Evidence scoring — evaluate each artifact category against the four sub-questions

Memory Acquisition Timing

T0 ─── Clean baseline (before execution)
T1 ─── During active execution / injection phase
T2 ─── Post-execution, pre-deletion (if applicable)
T3 ─── After disk artifact deletion (Experiments 04–05)

06 Experiment 01 — Process Hollowing

T1055.012 Process Injection: Process Hollowing

What the Technique Does

Attacker process
       │
       ▼
CreateProcess (CREATE_SUSPENDED)
       │  target: notepad.exe / svchost.exe
       ▼
NtUnmapViewOfSection
       │  original image unmapped from target
       ▼
VirtualAllocEx (PAGE_EXECUTE_READWRITE)
       │  new region in target address space
       ▼
WriteProcessMemory
       │  malicious PE written into region
       ▼
SetThreadContext / NtSetContextThread
       │  RIP/EIP redirected to malicious EP
       ▼
ResumeThread
       │
       ▼
Malicious code executes under target process name

Process hollowing exploits the gap between the process image reported by the OS and the actual code executing within that process. The legitimate process is created suspended; its image is unmapped via NtUnmapViewOfSection; a replacement PE is written into a newly allocated region; the thread context is redirected. After resumption, the process appears legitimate by name and PID but executes attacker-controlled code.

Expected Forensic Artifacts

VAD / PEB discrepancy. Under normal conditions, both the VAD tree and the PEB reference the same on-disk image. When hollowing occurs, the original VAD entry is removed after unmapping. The new region from VirtualAllocEx carries PAGE_EXECUTE_READWRITE — legitimately loaded image sections carry PAGE_EXECUTE_WRITECOPY and are file-backed.

Memory region typeTypical protectionVAD backing
Legitimate loaded PEPAGE_EXECUTE_WRITECOPYMapped file
Hollowed process regionPAGE_EXECUTE_READWRITEPrivate (none)
StackPAGE_READWRITEPrivate
HeapPAGE_READWRITEPrivate
Key indicator A PAGE_EXECUTE_READWRITE region at the process base address with a PE header (MZ / 4D 5A) and no mapped file backing is a strong hollowing indicator.

Volatility 3 Analysis

# Step 1 — Identify target process
vol.py -f T1_execution.mem windows.pstree

# Step 2 — Check the VAD for the process
vol.py -f T1_execution.mem windows.vadinfo --pid <PID>

# Step 3 — Run malfind against all processes
vol.py -f T1_execution.mem windows.malfind

# Step 4 — Check loaded modules vs LDR lists
vol.py -f T1_execution.mem windows.ldrmodules --pid <PID>

# Step 5 — Dump suspicious region
vol.py -f T1_execution.mem windows.dumpfiles --virtaddr <VAD_START>

# Step 6 — Run PE-sieve against live process at T1 for comparison

malfind indicators for hollowing: private VAD region at the process image base; PAGE_EXECUTE_READWRITE protection; MZ header present; no mapped file path. Note: PE-sieve / Hollows Hunter provides complementary detection — it compares the in-memory image against the on-disk file, catching mismatches that malfind misses.

Sysmon Correlation

  • EID 1 — CreateProcess with CREATE_SUSPENDED flag visible in process telemetry
  • EID 10 — ProcessAccess with PROCESS_VM_WRITE | PROCESS_VM_OPERATION from attacker to target
  • EID 25 — Process Tampering — high-fidelity signal when correlated with EID 1 and EID 10

07 Experiment 02 — Reflective / Manual PE Loading

T1620 Reflective Code Loading T1055.001

What the Technique Does

Attacker process holds PE in memory (from disk, network, or another source)
       │
       ▼
VirtualAlloc (PAGE_EXECUTE_READWRITE or PAGE_READWRITE → PAGE_EXECUTE_READ)
       │
       ▼
Manual mapping: copy PE headers and sections
       │
       ▼
Resolve imports manually
       │  (no LoadLibrary / LdrLoadDll on the payload itself)
       ▼
Apply relocations
       │
       ▼
Execute entry point or exported function

Reflective loading allows a PE to map and execute itself entirely within memory, without using the standard Windows loader (LdrLoadDll). Because the standard loader is bypassed, the DLL or executable does not appear in the process's LDR module lists — the structures queried by dlllist and ldrmodules. The module exists in executable memory but is invisible to the loader's linked lists.

Expected Forensic Artifacts

The ldrmodules plugin surfaces the discrepancy: columns InLoad, InMem, and InInit are all False for a module present in the VAD but not registered in the LDR lists. A legitimately loaded DLL will have True in all three columns.

If the attacker does not wipe or corrupt headers post-mapping, the MZ/PE header remains at the start of the allocation. malfind will surface it. The manually mapped PE resolves its own imports at runtime — resolved import addresses within the mapped PE's IAT will contain valid pointers into standard system DLLs, visible in a dump of the mapped region.

Volatility 3 Analysis

# Step 1 — Identify LDR list inconsistencies
vol.py -f T1_execution.mem windows.ldrmodules --pid <PID>
# Look for VAD entries with False/False/False in InLoad/InMem/InInit columns

# Step 2 — Confirm with malfind
vol.py -f T1_execution.mem windows.malfind --pid <PID>

# Step 3 — Inspect VAD permissions
vol.py -f T1_execution.mem windows.vadinfo --pid <PID>

# Step 4 — Dump the region and analyze headers
vol.py -f T1_execution.mem windows.dumpfiles --virtaddr <BASE>
# Open in PE-bear to inspect headers, imports, sections

Sysmon Correlation

  • EID 7 (Image Load) — A reflectively loaded DLL will not generate EID 7 because it does not go through the standard loader; absence of expected EID 7 for a behaviorally active module is a signal
  • EID 10 — If reflection occurs cross-process: ProcessAccess with write permissions from loader to host

Evidence Scoring

Exp 02 · Reflective Loading
Can the process be identified?HIGH — pslist / pstree
Can the malicious region be identified?HIGH — ldrmodules + malfind + vadinfo
Can the payload PE be extracted?HIGH (if headers intact)
Can strings / configuration be recovered?HIGH — strings on extracted region
Does evidence survive disk artifact deletion?YES — process holds mapping in memory
Limitation Implementations that wipe PE headers after mapping defeat header-based detection. Behavioral analysis of the executable region (disassembly, string extraction) can still recover useful intelligence.

08 Experiment 03 — Process Injection (APC / Shellcode)

T1055.004 Asynchronous Procedure Call T1055.002

What the Technique Does

Attacker process (Process A)
       │
       ├── OpenProcess(target PID)
       ├── VirtualAllocEx(target, PAGE_EXECUTE_READWRITE)
       ├── WriteProcessMemory(target, shellcode/PE)
       │
       ├── [APC path] QueueUserAPC(thread in target, alloc_addr) + ResumeThread
       │
       └── [Remote thread path] CreateRemoteThread(target, alloc_addr)

                    ↓
              Process B (legitimate: explorer, notepad, svchost)
              Executes attacker shellcode / PE under legitimate context

Expected Forensic Artifacts

Cross-process handle access. The attacker process must open a handle to the target. This generates EID 10 (Sysmon ProcessAccess) with PROCESS_VM_WRITE and/or PROCESS_VM_OPERATION in GrantedAccess, and a Process handle visible in windows.handles for the attacker process.

Executable private region in the target. The allocated shellcode/PE region in the target process is private, PAGE_EXECUTE_READWRITE at allocation time, and visible via vadinfo and malfind under the target process PID — not the attacker.

APC path note: QueueUserAPC does not generate Sysmon EID 8. EID 8 is specific to CreateRemoteThread. APC detection relies on the cross-process access pattern and resulting executable private region.

Volatility 3 Analysis

# Step 1 — Find suspicious processes
vol.py -f T1_execution.mem windows.pstree

# Step 2 — Check for injected regions in all processes
vol.py -f T1_execution.mem windows.malfind
# The injected region will appear under the TARGET process PID

# Step 3 — Inspect handles of attacker process
vol.py -f T1_execution.mem windows.handles --pid <ATTACKER_PID>
# Look for open Process handles pointing to legitimate target PIDs

# Step 4 — Check threads in the target process
vol.py -f T1_execution.mem windows.thrdscan --pid <TARGET_PID>

# Step 5 — Dump shellcode from target process
vol.py -f T1_execution.mem windows.malfind --dump
# Analyze with scdbg (shellcode emulation) or YARA

Evidence Scoring

Can the malicious region be identified?HIGH — vadinfo + malfind in target
Can shellcode/payload be extracted?HIGH — malfind dump

09 Experiment 04 — Unpacking in Memory

T1027.002 Software Packing T1140

What the Technique Does

DISK:
┌───────────────────────────────┐
│ Packed/encrypted PE           │
│ High entropy · Stub EP        │
│ Few meaningful strings        │
│ Minimal imports               │
└───────────────────────────────┘
                │ (execution begins)
        Unpacking stub runs:
        VirtualAlloc → decrypt → copy sections → resolve imports → jump
                │
                ▼
MEMORY:
┌───────────────────────────────┐
│ Unpacked PE in allocated region│
│ Original PE headers (MZ)      │
│ Readable strings              │
│ Full import table             │
│ Decrypted configuration       │
│ C2 addresses · Mutex names    │
└───────────────────────────────┘

A packer wraps the original payload in an outer stub. On disk: high entropy, minimal imports, opaque content. When executed, the stub allocates memory, decrypts or decompresses the inner payload, and transfers execution. The inner payload must exist in decrypted form in memory to execute — giving analysts a recovery window.

Key malfind Criteria

windows.malfind filters for memory regions meeting all of the following: private backing (not file-backed); executable permissions (PAGE_EXECUTE_READ, PAGE_EXECUTE_READWRITE, PAGE_EXECUTE_WRITECOPY); suspicious content (PE header present or shellcode-like heuristics).

Limitation: malfind does not catch hollowing implementations that do not involve private executable memory. PE-sieve / Hollows Hunter provides complementary coverage by comparing in-memory images against on-disk counterparts for all loaded processes.

ldrmodules Interpretation

A legitimately loaded DLL will show True in all three columns. A reflectively loaded or manually mapped DLL will typically show False / False / False — present in the VAD but never registered with the loader. This is one of the strongest single-plugin signals for reflective loading.

The critical timing constraint Memory forensics is bounded by process lifetime. Evidence exists in memory from execution until process termination. Acquire memory as early as possible. Every minute of delay is time in which the process could terminate, the attacker could perform cleanup, or evidence could be paged out.

14 Detection Opportunities

Cross-Experiment Detection Patterns

Executable private memory with PE header (malfind signal) — Appears in all five experiments. All five produce private executable VAD regions containing PE headers or shellcode. malfind is the primary automated detection mechanism. False positive management requires baselining legitimate JIT compilers, security software self-protection, and game anti-cheat engines.

LDR list inconsistency (ldrmodules signal) — A module present in the VAD but absent from all three LDR lists (InLoad/InMem/InInit = False/False/False) with executable permissions is a high-confidence reflective loading indicator.

Cross-process handle access with write rights (Sysmon EID 10) — PROCESS_VM_WRITE | PROCESS_VM_OPERATION from a non-system source process to a legitimate target process is a strong injection precursor signal.

Process tampering (Sysmon EID 25) — High-priority signal when correlated with EID 1 and EID 10. Do not assume universal coverage — depends on Sysmon configuration and implementation specifics.

Network connections from unexpected process images (netscan) — A legitimate process image (notepad.exe, svchost.exe) with unexpected outbound connections is a behavioral signal independent of injection technique. Network state is recorded in kernel socket structures and survives EDR user-mode hook removal.

Conceptual YARA — Private Executable PE in Memory

rule Private_Executable_PE_In_Memory {
    meta:
        description = "MZ header in private executable memory region"
        context     = "Memory forensics — malfind output"
        note        = "Validate against known-good JIT and security software before tuning"
    strings:
        $mz = { 4D 5A }
    condition:
        $mz at 0 and filesize < 50MB
}

Conceptual YARA — Reflective Loader Stub

rule Reflective_Loader_Stub {
    meta:
        description = "Reflective DLL loader heuristics"
        note        = "Signatures vary across loader implementations; tune for environment"
    strings:
        $peb_access  = { 65 48 8B 04 25 60 00 00 00 }   // PEB access via GS
        $reflstr     = "ReflectiveLoader" ascii wide
    condition:
        any of them
}

15 Limitations

Memory Forensics Does Not Provide

  • Evidence after process termination — once the process exits, memory mappings are released; recovery from unallocated physical pages is possible but unreliable
  • Evidence after reboot — volatile memory is cleared on power cycle
  • Complete coverage of all injection techniques — DKOM manipulation, kernel-mode rootkits, hardware-based techniques, and sleep obfuscation with protected regions are outside the scope of user-mode Volatility analysis
  • Real-time detection — memory forensics operates on acquired images; it is post-hoc analysis, not live prevention

Tool Limitations

  • malfind false positives — JIT compilers (.NET, JavaScript engines), security products, and game anti-cheat engines produce private executable regions that are not malicious. Every malfind hit requires analyst triage
  • malfind false negatives — hollowing implementations using file-backed mappings are not detected by malfind alone; PE-sieve provides complementary coverage
  • ldrmodules — implementations that manually insert forged LDR entries can defeat this check; cross-validate with VAD permissions and malfind
  • Header wiping — implementations that zero out PE headers post-mapping defeat header-based identification; shellcode-level analysis and behavioral signatures provide fallback
  • Anti-forensic VAD manipulation — advanced attackers can manipulate VAD node structures to remove suspicious entries; psscan (scanning physical memory) may still find residual EPROCESS structures
Research scope This project uses controlled, representative samples in an isolated lab environment. Results may differ with advanced commercial malware that implements active anti-forensic measures, header wiping, or encrypted memory regions. Findings represent the baseline forensic opportunity, not a guarantee of recovery in every real-world engagement.

16 Conclusions

Central Finding

Memory forensics recovered meaningful evidence in every experiment. Across all five techniques, the combination of malfind, vadinfo, ldrmodules, netscan, and process memory extraction produced:

  • Identification of the malicious process or injected region in 5 of 5 experiments
  • Payload extraction in 5 of 5 experiments (with caveats for header corruption)
  • String and C2 recovery in 5 of 5 experiments
  • Evidence survival after disk artifact deletion in 5 of 5 experiments
Execution in memory requires memory. Every execution technique studied creates structural residue in the Windows VAD tree, process structures, and kernel data — residue that persists independently of what happens to the disk artifact that started execution.

Implication for DFIR Practice

Acquire memory early. The window of opportunity begins at execution and ends at process termination. Earlier acquisition means richer evidence. Waiting until disk analysis is complete risks losing the best forensic surface in a fileless attack.

Do not treat disk analysis as the primary forensic surface for in-memory malware. In fileless and injection scenarios, disk analysis answers few of the important questions. Memory analysis answers most of them.

Correlate memory with endpoint telemetry. The strongest reconstructions combine Volatility findings (what was in memory) with Sysmon and Procmon telemetry (what operations occurred). Neither source alone provides a complete picture.

Final Answer

Answer to the research question

Substantial evidence remains. Across representative fileless and injection scenarios, a trained analyst with Volatility 3 and PE-sieve can reliably identify the malicious process, recover the payload, extract decrypted configuration and C2 information, and reconstruct attacker intent — even after the original disk artifact has been deleted — as long as memory is acquired while the process is still running.

Memory tells the truth.

18 Defensive Recommendations

  1. Acquire memory early in any suspected intrusion. Memory forensics is time-bounded by process lifetime. Treat memory acquisition as a first-response action alongside disk imaging, not a secondary step.
  2. Deploy Sysmon with a maintained configuration. Enable at minimum: EID 1, 3, 7, 8, 10, 11, 22, 25. EID 10 (ProcessAccess) and EID 25 (Process Tampering) are particularly valuable for injection and hollowing detection.
  3. Forward endpoint telemetry to a SIEM in real-time. Attackers who delete event logs cannot retroactively remove events already received by a remote SIEM.
  4. Integrate PE-sieve / Hollows Hunter into incident response workflow. Where live analysis is possible, PE-sieve provides complementary detection to Volatility's malfind, catching hollowing cases that involve file-backed regions.
  5. Prioritize behavioral detection over signature-based detection for in-memory threats. Packed, encrypted, and reflectively loaded payloads defeat most static signatures. Behavioral rules targeting the execution sequence are more durable.
  6. Develop memory forensics capability within the DFIR team. Regular training on representative scenarios is necessary to build analyst confidence before an actual incident.
  7. Run periodic memory integrity scanning in production. Short-interval or triggered scanning of running processes for malfind-class indicators provides early detection of injection attempts. Tune thresholds against known JIT and security software baselines.
