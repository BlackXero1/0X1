Memory Tells the Truth

The disk was clean. The EDR was quiet. The malware was still running. Here's how I caught five kinds of fileless malware using nothing but a RAM dump.

📅 2026-11-20 🔖 Volatility 3 · PE-sieve · Sysmon ⏱ 14 min read
TL;DR
  • I ran five in-memory techniques: process hollowing, reflective loading, APC injection, in-memory unpacking, and a self-deleting payload. I captured RAM at each stage.
  • In all five, Volatility 3 found the malicious region, dumped the payload, and recovered C2 strings. That held even after the file on disk was gone.
  • The catch: it only works while the process is alive. Reboot the box and it's all gone.
  • The lesson for responders: grab memory first, image the disk second.

Picture a familiar incident. A host is beaconing to a domain nobody recognises. You pull the disk image and find nothing. There's no dropped executable, no persistence key, nothing odd in Prefetch. The binary that started it all deleted itself an hour ago.

For a disk-first investigation, that's a dead end. But the beacon is still going out, which means something is executing. And anything that executes on Windows has to live in memory.

That idea is the whole post. Attackers can encrypt files, delete them, or never write them at all. What they can't do is run code without the operating system tracking where that code lives. I wanted to measure how far that idea really goes, so I built five experiments and attacked each one with a memory image.

01 Why disk forensics loses this fight

Modern loaders are built to beat the disk. A packed binary shows you high entropy and a stub. A reflectively loaded DLL never touches the Windows loader at all. A hollowed process carries a legitimate name on disk with someone else's code inside it. A self-deleting dropper leaves no file behind.

But each of those tricks has a cost in memory that the attacker can't fully control:

  • The kernel's VAD tree records every allocation and its protection flags.
  • Most payloads write a PE header into memory before they run.
  • The kernel keeps the parent/child process relationships.
  • Socket state for C2 connections sits in kernel structures.
  • To execute, the payload has to decrypt itself, so for some window its config is plaintext.
A process can hide an API call. It can't hide the memory it's running from.

02 The setup

I kept it simple and repeatable. The target was a Windows 10 22H2 x64 VM with 4 vCPUs and 8 GB RAM, on a host-only network with a local listener standing in for C2. Each run started from a clean snapshot. Sysmon was running with the SwiftOnSecurity config, alongside Procmon and Wireshark.

The important part is when I captured memory. I took up to four images per experiment with WinPmem:

T0  clean baseline        ── before anything runs
T1  during execution      ── injection / unpacking in progress
T2  after activity        ── payload settled, C2 up
T3  after file deletion   ── disk artifact gone (Exp 04–05)

Comparing T0 to T1 tells you what changed. Comparing T2 to T3 tells you what survives cleanup. That's the question that matters in a real investigation.

I used Volatility 3 for analysis, then PE-sieve and Hollows Hunter to cross-check on the live VM. I used PE-bear and IDA Free on anything I dumped.

03 My triage order

Running every plugin and reading the output top to bottom wastes hours. Every experiment used the same order, and each step answers one question:

# 1. What's running, and who started it?
vol -f mem.raw windows.pstree
vol -f mem.raw windows.psscan        # catches unlinked / exited processes
vol -f mem.raw windows.cmdline

# 2. Where is there executable memory that shouldn't exist?
vol -f mem.raw windows.malfind

# 3. Is anything loaded that the loader doesn't know about?
vol -f mem.raw windows.ldrmodules --pid <PID>

# 4. What does the address space look like?
vol -f mem.raw windows.vadinfo --pid <PID>

# 5. Who is it talking to?
vol -f mem.raw windows.netscan

# 6. Pull the region out and read it
vol -f mem.raw -o out/ windows.vadinfo --pid <PID> --address <VAD_START> --dump

Two of these do most of the work. malfind flags private, executable memory that looks like code or a PE. ldrmodules compares the VAD tree against the loader's three module lists. Anything mapped as an image but missing from all three lists was never loaded the normal way.

04 Experiment 1: Process hollowing

T1055.012

The trick

Start notepad.exe suspended. Unmap its image with NtUnmapViewOfSection. Allocate new memory, write a different PE into it, point the thread's RIP at the new entry point, and resume. Task Manager shows notepad, but the code running is the attacker's.

What it left behind

The disguise breaks at the memory protection level. A normally loaded image is file-backed and its sections are PAGE_EXECUTE_WRITECOPY. The hollowed region was private, PAGE_EXECUTE_READWRITE, and began with 4D 5A. It was a PE with no file behind it, sitting where notepad's image should have been.

RegionProtectionBacking
Normal loaded imageEXECUTE_WRITECOPYMapped file
Hollowed payloadEXECUTE_READWRITEPrivate, none

The PEB still claimed the process was C:\Windows\System32\notepad.exe. When the PEB and the VAD tree disagree like this, that disagreement is your finding.

Sysmon backed it up. EID 1 showed the suspended child. EID 10 showed PROCESS_VM_WRITE access from the parent. EID 25 (Process Tampering) fired on the image change.

Where malfind falls short Variants that hollow through a file-backed section, such as phantom DLL hollowing, don't create private executable memory, so malfind stays silent. PE-sieve catches them because it compares each in-memory image against its file on disk. Run both.
VerdictProcess found, region found, PE dumped, strings recovered. It all survived as long as the process stayed alive.

05 Experiment 2: Reflective DLL loading

T1620

The trick

Skip LoadLibrary entirely. The loader stub allocates memory, copies the headers and sections over, fixes relocations, resolves its own imports, and calls the entry point. Because LdrLoadDll never runs, the DLL never shows up in the PEB's module lists. dlllist can't see it, and Sysmon EID 7 (Image Load) never fires.

What it left behind

Two things. First, a private executable region that starts with an MZ header, which malfind picks up straight away. Second, a mismatch in ldrmodules:

Base            InLoad  InInit  InMem  MappedPath
0x7ff8a1b00000  True    True    True   \Windows\System32\kernel32.dll
0x1d4c0a50000   False   False   False  <none>   ← here it is

I dumped the region and opened it in PE-bear. Even though nothing had registered it, the IAT was fully resolved with live pointers into kernel32 and ws2_32. That's enough to understand what the payload does without ever having the original file.

Missing telemetry is a clue in its own right. A process making network connections from code with no EID 7 behind it deserves a closer look.

VerdictDetected and dumped. The one real limit is loaders that wipe their own PE header after mapping. Then you're left analyzing raw code, but malfind still flags the region.

06 Experiment 3: APC shellcode injection

T1055.004

The trick

Open a handle to a legitimate process. Use VirtualAllocEx to allocate RWX memory, write shellcode with WriteProcessMemory, and run it with QueueUserAPC on one of its threads. The Early Bird variant queues the APC on a freshly created suspended process before the process's own startup code runs.

What it left behind

The evidence sits in two processes, which is easy to miss:

  • The victim holds the payload. malfind flags the RWX region under the target's PID, not the injector's.
  • The injector holds the handle. windows.handles --pid <injector> showed an open Process handle to the target.

One correction to a common mistake: Sysmon EID 8 does not fire for APC injection. EID 8 only covers CreateRemoteThread. For APC injection, the Sysmon evidence is EID 10, meaning cross-process access with VM_WRITE and VM_OPERATION rights. If your detection waits for EID 8, it will miss this.

The dumped shellcode was small, but running strings on it gave me the listener IP straight away. netscan then showed an established connection from a process that has no reason to be on the network.

VerdictInjected region found in the victim, injector tied to it through the handle table, C2 recovered.

07 Experiment 4: Unpacking in memory

T1027.002T1140

The trick

On disk, the sample was a packed stub: entropy above 7.0, a handful of imports, no readable strings. That's all static analysis gets. At runtime the stub allocates memory, decrypts the real payload into it, and jumps there.

What it left behind

For the payload to run, it had to be decrypted. At T1, the largest private executable region in the process was the complete inner PE:

ArtifactOn diskIn memory (T1)
ImportsStub onlyFull IAT
StringsEncryptedReadable
C2 configEncryptedPlaintext
Mutex nameAbsentPresent

This is the most practical result of the five. Even if you never plan to do forensics, dumping memory is often the quickest way to unpack a sample. The packer has already done the decryption for you.

Timing matters Some unpackers free or wipe the decrypted copy after handing off execution. T1 captures beat T2 captures. Snap memory as early as you can.
VerdictInner payload, imports, config, and C2 all recovered from memory, none of which were visible on disk.

08 Experiment 5: The disappearing dropper

T1070.004T1055

The trick

This is the scenario from the opening. The sample runs, sets up C2, and deletes its own executable.

One detail is worth knowing. Windows normally won't let you delete a running .exe because the image section holds the file open. Self-deleting malware works around this by renaming its default data stream to an ADS and then setting delete-on-close through SetFileInformationByHandle. The file vanishes from the directory listing even though the process is still running.

What it left behind

At T3 the disk was clean. Memory showed:

DISK (T3)                         MEMORY (T3)
─────────                         ───────────
malware.exe   ✗ gone              process in pslist        ✓
                                  original path in PEB     ✓
                                  PE header in VAD         ✓
                                  decrypted config         ✓
                                  live C2 in netscan       ✓
                                  FILE_OBJECT in filescan  ✓

Every artifact I needed was still there. I recovered the payload from the process's own image mapping, which is better than carving the disk, because it's the decrypted, relocated, running version.

VerdictFull reconstruction after deletion. But when I killed the process and captured again, recovery fell to scattered pages. After a reboot, nothing was left.

10 Turning this into detections

Five signals showed up across all the experiments. These are what I'd build hunts around:

  1. Private executable memory that starts with MZ. This is the malfind signal. Baseline JIT engines (.NET, V8), anti-cheat, and your own EDR, or you'll drown in false positives.
  2. Image-mapped VADs missing from all three LDR lists. High confidence for reflective loading.
  3. Sysmon EID 10 with VM_WRITE from a non-system process into explorer, svchost, or notepad. This precedes almost every injection.
  4. Sysmon EID 25. Rare and high-signal. Make sure your config actually enables it.
  5. Network activity from processes that shouldn't have any. This doesn't depend on technique, and user-mode unhooking doesn't affect it.

Two YARA starters for scanning dumped regions. Treat them as hunting leads, not verdicts:

rule Mem_Private_PE {
    meta:
        description = "PE at start of a dumped private region"
    strings:
        $mz = { 4D 5A }
        $pe = "This program cannot be run" ascii
    condition:
        $mz at 0 and $pe in (0..0x200)
}

rule Mem_Reflective_Loader_Hint {
    meta:
        description = "PEB walk via GS + ReflectiveLoader export"
    strings:
        $peb  = { 65 48 8B 04 25 60 00 00 00 }   // mov rax, gs:[0x60]
        $name = "ReflectiveLoader" ascii
    condition:
        $peb and $name
}

11 What memory won't tell you

Here are the limits, so you don't over-trust these results:

  • Sleep obfuscation (Ekko and similar) encrypts the implant and sets its pages to no-access between beacons. Capture at the wrong moment and malfind sees nothing readable.
  • Header wiping defeats MZ-based hunting. You fall back to code heuristics.
  • Forged LDR entries can make ldrmodules look clean. Cross-check against VAD protections.
  • Kernel rootkits and DKOM are outside the scope of this work. psscan sometimes finds what pslist can't, but not always.
  • False positives are real. Every malfind hit needs someone to look at it.

These were controlled samples on a clean VM. Mature commercial implants put real effort into anti-forensics, so treat these results as a baseline, not a guarantee.

12 Takeaways for responders

If you remember one thing

Capture memory before you do anything else. Don't reboot, isolate in a way that kills processes, or wait for the disk image to finish. Every minute the process might exit is evidence you might lose.

  • Memory first, disk second for anything that looks fileless.
  • Correlate. Volatility tells you what was in memory, and Sysmon tells you how it got there. You need both to tell the full story.
  • Forward telemetry off-host in real time so log clearing can't erase your timeline.
  • Pair Volatility with PE-sieve. They catch different kinds of hollowing.
  • Practise on known samples before the real incident. Reading malfind output takes experience.

Attackers can delete their files, encrypt their payloads, and hide in other processes. While their code is running, though, it has to be somewhere in memory, and that's where you'll find it.

Memory tells the truth. You just have to ask before it forgets.
