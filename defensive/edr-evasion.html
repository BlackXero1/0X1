The Cat-and-Mouse Game

EDR Evasion in the Wild: What Attackers Blind — and What Defenders Can Still See

Date 10 August 2026 Classification TLP:CLEAR Audience SOC Analysts · Detection Engineers · Threat Hunters Perspective Defensive Detection Engineering Scope Windows endpoint telemetry and EDR evasion

An EDR is not a single sensor sitting between an attacker and the operating system.

It is a collection of telemetry sources, prevention mechanisms, memory inspection capabilities, behavioral analytics, and cloud correlation operating at different layers.

Attackers increasingly target individual layers of that visibility: AMSI, user-mode ETW, ntdll hooks, memory scanners, process ancestry, and thread-creation telemetry.

But bypassing one sensor does not make the underlying behavior disappear.

A process can hide an API call. It cannot hide the operation it ultimately needs to perform.

A payload can encrypt its memory while sleeping, but it must eventually decrypt and execute. A forged parent can disguise ancestry, but independent telemetry may expose inconsistencies. Direct syscalls can bypass user-mode hooks, but they do not make the resulting kernel operation cease to exist.

That is the real EDR cat-and-mouse game: not visibility versus invisibility, but telemetry versus telemetry reduction.

EDR evasion is not invisibility. It is telemetry reduction.

Attackers increasingly target individual observation layers — AMSI, user-mode ETW, ntdll hooks, memory scanners, process ancestry, and thread-creation telemetry. The defensive response is not to depend on a single sensor, but to correlate independent process, memory, file, identity, and network observations.

How EDR Telemetry Actually Works

Before discussing evasion, understand the layers an EDR can draw from:

Key insight: Most evasion techniques in this article bypass one or two of these layers, not all of them. The article distinguishes between user-mode telemetry bypass and complete visibility loss.

Scope & Limitations

This article focuses on user-mode evasion against Windows endpoint telemetry. It does not claim that every EDR implements the telemetry layers described here, nor that kernel telemetry is universally available or immune to sensor failure, privileged compromise, or configuration gaps. Detection examples are conceptual unless explicitly identified as product-specific.

The Detection Engineering Rule: Correlate Across Layers

EDR evasion is usually telemetry reduction, not invisibility.

The practical question for defenders is therefore not "Did the attacker bypass the EDR?" but "Which telemetry source did they bypass, which independent sources remain, and can we correlate them?"

A single evasion artifact rarely provides enough evidence by itself. The strongest detections combine process, memory, file, identity, and network telemetry.

AMSI modification:
PowerShell process → suspicious memory write → amsi.dll modification → missing/abnormal AMSI telemetry → outbound connection
Sleep obfuscation:
Private executable memory → protection change → encrypted/modified region → repeated timing → network beacon
Process hollowing:
Suspended process creation → cross-process memory access → image modification → execution from inconsistent memory → network activity
PPID spoofing:
Claimed parent → token mismatch → unusual handle access → command-line anomaly → independent creator telemetry
Direct syscall:
Unusual executable memory/call context → native operation → kernel-observed activity → suspicious downstream behavior

The important detection is not the individual API call. It is the behavioral sequence. Effective detection engineering models dependencies between attacker actions, not just individual artifacts — because evasion removes artifacts, but it cannot remove the dependencies between the steps an attacker must take.

Technique 01: Anti-Analysis Evasion

MITRE ATT&CK: T1497 (Virtualization/Sandbox Evasion), T1622 (Debugger Evasion)
Evidence: Observed in the wild + reproduced in lab

What the attacker does

Reads PEB fields such as BeingDebugged and NtGlobalFlag, and heap ForceFlags directly from memory — no API calls. These offsets are architecture- and Windows-version-dependent; implementations target the specific PEB layout of the intended platform. RDTSC/QPC-based timing comparisons can detect execution delays associated with debugging, instrumentation, or virtualization. CPUID leaf 0x40000000 can expose hypervisor/vendor identification information that malware may use as a virtualization indicator.

What it bypasses

  • User-mode API hooks (no API call made — direct memory read)
  • Sandbox/analysis environment detection

What remains visible

  • Process creation (Sysmon EID 1, Windows Security EID 4688)
  • Process termination (Sysmon EID 5, Windows Security EID 4689) — correlate short-lived processes with suspicious parents
  • Process-creation callbacks can remain available to security products independently of user-mode hooks, provided the relevant kernel telemetry is deployed and functioning

Detection opportunities

Environment-discovery execution pattern: A short-lived process that performs environment discovery, timing checks, virtualization checks, or debugger detection before terminating is a stronger signal of sandbox or debugger evasion than short execution time alone. Legitimate installers, updaters, CLI tools, and helper processes also exhibit short-lived execution, so do not treat a specific time threshold as a universal detection rule. This is a behavioral pattern requiring correlation, not a single event.

Defensive controls

Sandbox realism — configure analysis VMs with:

  • 4+ logical CPUs and 8+ GB RAM
  • 1920x1080+ screen resolution
  • Realistic uptime (not freshly booted)
  • Installed browser with history, documents in user folders
  • Mouse/keyboard activity simulation
  • Hypervisor fingerprint reduction: minimize exposed virtualization artifacts
  • Correct locale/timezone for target region

Technique 02: AMSI Tampering

MITRE ATT&CK: T1562.001 (Impair Defenses: Disable or Modify Tools)
Evidence: Observed in the wild + publicly implemented

What the attacker does

Modifies the in-memory implementation of AmsiScanBuffer in amsi.dll so that calls return without performing the expected scan. One commonly observed patch pattern replaces the function prologue with a short return sequence (e.g., xor eax,eax; ret), although the exact patch varies across implementations and Windows builds.

Note: AmsiScanBuffer returns an HRESULT; the scan result is delivered through the [out] AMSI_RESULT* parameter. Applications should use AmsiResultIsMalware() to evaluate the result. The patch prevents the scan function body from executing at all.

What it bypasses

  • AMSI user-mode scanning path within the compromised process
  • PowerShell, .NET, and other AMSI-integrated application scanning

What remains visible

  • Kernel-level telemetry available to the EDR may continue to observe process, memory, file, or downstream behavioral activity independently of the AMSI scanning path
  • EDR products may have additional behavioral, memory, or cloud-based detection independent of the modified AMSI call path
  • Memory scanning can detect the modified function prologue

Detection opportunities

Illustrative memory-scanning logic:

rule AMSI_Prologue_Modified {
    meta:
        description = "Illustrative logic for AmsiScanBuffer prologue modification"
        severity = "HIGH"
        note = "Validate against target Windows build - prologue varies"
    strings:
        $patch1 = { 31 C0 C3 }        // xor eax,eax; ret
        $patch2 = { B8 57 00 07 80 }   // mov eax, 0x80070057; (E_INVALIDARG)
        $amsi   = "AmsiScanBuffer" ascii wide
    condition:
        any of ($patch*) and $amsi
}

Important: This rule searches for the patch bytes and function name independently — it does not verify the patch is located at the AmsiScanBuffer function address. A production rule should resolve the function address from the loaded module and validate the bytes at that address.

Defensive controls

  • Enable VBS/HVCI and other platform integrity controls where compatible
  • Use EDR capabilities that detect in-memory modification of security-sensitive modules
  • Monitor for writable/executable memory transitions and modifications to loaded security-related DLLs
  • Baseline AMSI-integrated application behavior and investigate suspicious gaps

Technique 03: ETW Tampering

MITRE ATT&CK: T1562.001 (Impair Defenses: Disable or Modify Tools)
Evidence: Observed in the wild + publicly implemented

What the attacker does

Writes a single 0xC3 (ret) byte at the entry point of EtwEventWrite in ntdll.dll. This suppresses ETW events generated through that user-mode path within the compromised process.

Microsoft documents EtwEventWrite as internal to the operating system and subject to change from one release of Windows to another.

What it bypasses

  • User-mode ETW event generation through the patched EtwEventWrite path
  • May suppress user-mode ETW events generated through the affected process's patched path, potentially including telemetry associated with PowerShell activity (EID 4104) and other user-mode provider events. This does not mean that all ETW telemetry generated by Windows or other processes is suppressed

What remains visible

  • Telemetry generated independently of the compromised process's user-mode ETW path may remain available, depending on the provider and collection architecture
  • Events already forwarded to a SIEM before the patch was applied
  • Events from other processes (the patch only affects the patching process)

Detection opportunities

Missing telemetry is evidence of a visibility gap, not proof of ETW tampering.

Absence of expected telemetry is a signal, but requires correlation:

A PowerShell process that normally generates Script Block Logging events (EID 4104) but produces none during its lifetime — while also exhibiting suspicious execution behavior (unusual parent, unsigned binary, network activity) — should be investigated for telemetry tampering, policy misconfiguration, or alternate execution paths.

Do not treat missing EID 4104 alone as proof of ETW patching. Legitimate causes include: Constrained Language Mode, group policy changes, PowerShell version differences, and logging configuration.

Recommended approach: Baseline expected ETW event rates per process type over 2+ weeks. Alert on statistically significant deviations combined with other suspicious indicators.

Defensive controls

  • Where available, rely on kernel-level ETW providers which operate independently of user-mode patching
  • Forward logs to a remote SIEM immediately — an attacker who patches ETW cannot retroactively delete events that were already successfully received and retained by an independently controlled SIEM
  • Ask the EDR vendor which kernel-level telemetry sources they use and whether ETW-TI is part of that telemetry architecture

Technique 04: NTDLL Unhooking

MITRE ATT&CK: T1562.001 (Impair Defenses: Disable or Modify Tools)
Evidence: Publicly implemented + behavior reviewed

What the attacker does

Maps a fresh copy of ntdll.dll from disk using CreateFileMapping with SEC_IMAGE, locates the .text section, and overwrites part or all of the in-memory (potentially hooked) .text with the clean on-disk copy. The exact scope of the overwrite varies by implementation.

What it bypasses

  • Inline hooks present in ntdll's .text section at the time of overwrite
  • EDR interception of Nt* function calls that relied on those specific hooks

What remains visible

  • Kernel callbacks (PsSetCreateProcessNotifyRoutineEx, ObRegisterCallbacks, MiniFilter) — these can remain available to security products at kernel level, provided the relevant drivers are deployed and functioning
  • File access audit — the process opens ntdll.dll as a file
  • Memory mapping, section replacement, or protection changes associated with the affected ntdll region may provide supporting evidence, depending on implementation
  • Image-load telemetry (Sysmon EID 7) may provide supporting evidence

Detection opportunities

The detection rules in this article are conceptual, not production-ready Sigma rules. Field names, event sources, and available telemetry vary by EDR, Sysmon configuration, Windows version, and collection architecture.

Multi-event correlation (conceptual Sigma-style logic):

Correlate the following sequence within a single process:

  1. File access to \Windows\System32\ntdll.dll (not by a system process)
  2. SEC_IMAGE file mapping creation
  3. Memory protection change (PAGE_EXECUTE_WRITECOPY) on a region overlapping ntdll's loaded address range
  4. A substantial write or section replacement affecting the loaded ntdll .text region

Each event alone has legitimate explanations. The sequence together is high-confidence.

Defensive controls

  • Invest in EDR products with kernel-mode drivers using kernel callbacks and MiniFilter drivers — these are not affected by ntdll unhooking
  • Enable Kernel Data Protection (KDP) on supported hardware
  • User-mode hooks are fundamentally removable by any ring-3 code — do not treat them as a reliable sole detection mechanism

Technique 05: Sleep Obfuscation (Ekko-style)

MITRE ATT&CK: T1497.003 (Virtualization/Sandbox Evasion: Time Based Checks)
Evidence: Publicly implemented (5pider/Ekko) + behavior reviewed

Note: in-memory encryption during sleep should not automatically be mapped to T1027 or T1027.013 unless the implementation includes obfuscation of file content covered by that technique; T1027.013 specifically concerns encrypted or encoded file content on disk or during delivery.

What the attacker does

Before entering a C2 beacon sleep, the implant may encrypt or otherwise transform selected executable memory regions (using XOR, AES, RC4, or other mechanisms), flip page protection (commonly to PAGE_NOACCESS), and sleep. During the sleep window, a scanner that encounters the protected region may be unable to inspect the plaintext code, reducing the effectiveness of signature-based memory scanning during that interval.

What it bypasses

  • Memory scanning during the sleep window (encryption combined with inaccessible page protections can substantially reduce the usefulness of memory pattern matching during the sleep interval)
  • Static shellcode signatures in memory

What remains visible

  • Memory protection transition events — the encrypt/decrypt cycle requires VirtualProtect calls
  • The plaintext window between wake-up and re-encryption
  • Network beaconing pattern (the implant must communicate eventually)

Detection opportunities

Memory protection cycling: A private executable region that transitions between executable and NOACCESS states repeatedly is unusual and should be investigated, particularly when combined with encryption/decryption activity and periodic network beaconing.

This transition can occur in legitimate software (JIT compilers, game engines, security products), so treat it as a triage signal requiring correlation, not a standalone detection.

Telemetry source: Where the EDR or telemetry stack collects suitable kernel virtual-memory events, memory-protection transitions may be observable through kernel instrumentation and relevant ETW providers (such as Microsoft-Windows-Kernel-VirtualMemory). Note: Sysmon EID 10 is ProcessAccess (confirmed by Microsoft documentation), not a generic VirtualProtect event — do not conflate them.

title: Suspicious Memory Protection Cycling on Private Executable Region
status: experimental
description: >
    Detects repeated VirtualProtect transitions from executable to NOACCESS
    on the same private memory region, which may indicate sleep obfuscation.
logsource:
    category: process_tampering   # requires EDR/ETW memory telemetry
    product: windows
detection:
    selection:
        EventType: 'ProtectionChange'
        NewProtection: 'PAGE_NOACCESS'
        OldProtection|contains:
            - 'PAGE_EXECUTE_READWRITE'
            - 'PAGE_EXECUTE_READ'
        MemoryType: 'Private'
    condition: selection | count() by ProcessId, BaseAddress > 2
level: high
falsepositives:
    - JIT compilers
    - Game anti-cheat engines
    - Security software self-protection
note: >
    This rule requires EDR memory telemetry that logs VirtualProtect
    transitions. Standard Sysmon does not produce this event.

Defensive controls

  • Use the shortest practical periodic memory-scanning interval supported by the EDR and environment
  • Alert on repeated protection cycling on the same private executable region
  • Correlate with network beaconing patterns — an implant that sleeps must eventually wake and communicate

Technique 06: Direct Syscalls (Hell's Gate / Tartarus Gate)

MITRE ATT&CK: T1106 (Native API)
Evidence: Publicly implemented + behavior reviewed

Direct syscalls are primarily an interception-evasion mechanism — they bypass a specific telemetry collection point, not the underlying operation itself. The technique is not inherently malicious; it is the context in which it is used that determines intent.

What the attacker does

Instead of calling Nt* functions through ntdll.dll (where EDR hooks live), the attacker resolves the System Service Number (SSN) by reading the stub bytes directly from ntdll's export table, then issues a raw syscall instruction. The kernel receives the call normally, but the EDR's user-mode hook is never on the call path.

Tartarus Gate extends this: if the target stub is hooked, the SSN is inferred from neighboring unhooked stubs by ordinal offset.

Direct syscalls do not hide the resulting kernel operation; they primarily remove a user-mode interception point.

Defender takeaway: If your EDR relies solely on user-mode ntdll hooks for visibility into Nt* calls, direct syscalls render that telemetry layer unreliable. Prioritize kernel-level telemetry sources (ETW-TI, kernel callbacks) that observe the operation regardless of how it was invoked.

What it bypasses

  • The specific ntdll hooks that would otherwise intercept the targeted call

What remains visible

  • Kernel callbacks — PsSetCreateProcessNotifyRoutineEx, ObRegisterCallbacks, MiniFilter drivers may remain available regardless of how the system call was issued, depending on the EDR architecture, enabled providers, sensor health, and configuration
  • Where supported and collected, ETW Threat Intelligence (ETW-TI) can provide kernel-level telemetry relevant to system-call and threat activity
  • Depending on the EDR's kernel instrumentation and call-stack collection capabilities, a syscall whose user-mode return/call context points outside expected system-call stubs may provide an anomalous signal

Detection opportunities

  • EDR products with kernel telemetry (ETW-TI, kernel callbacks) may still observe the operation — they lose the user-mode call stack context but may retain the event itself, depending on EDR architecture, enabled providers, sensor health, and configuration
  • Call stack analysis: depending on sensor capabilities, a syscall return address pointing outside ntdll may be detectable as anomalous by kernel instrumentation

CET (Control-flow Enforcement Technology) — nuance

CET provides hardware-enforced shadow stack protection on Intel 11th gen+ and AMD Zen 3+. It hardens control flow integrity but should be treated as a hardening control, not a dedicated direct-syscall detection mechanism.

Defensive controls

  • Prioritize EDR vendors with kernel telemetry (ETW-TI, kernel callbacks) over those relying solely on user-mode hooks
  • Enable CET where hardware supports it — defense-in-depth, not a silver bullet
  • Direct syscalls make user-mode-hook-only EDR telemetry unreliable — design detection around kernel and network signals

Technique 07: Process Injection — Early Bird APC

MITRE ATT&CK: T1055.004 (Process Injection: Asynchronous Procedure Call)
Evidence: Observed in the wild + reproduced in lab

MITRE documents Early Bird as a variation where "malicious code can be written and executed before the process' entry point (and potentially subsequent anti-malware hooks)."

What the attacker does

Creates a target process (notepad, svchost) with CREATE_SUSPENDED. Allocates memory and writes shellcode via VirtualAllocEx + WriteProcessMemory (or Nt* equivalents). Queues an APC to the main thread via QueueUserAPC, then resumes the thread. The technique can execute code before some target-process user-mode instrumentation has initialized, depending on the security product and injection path.

What it bypasses

  • EDR user-mode instrumentation in the target process (the APC can execute before the EDR DLL initializes, depending on the product)

What remains visible

  • Process creation (Sysmon EID 1, Windows Security EID 4688) — the suspended process creation is visible
  • Process access (Sysmon EID 10) — cross-process handle operations with suspicious access rights
  • Process-creation callbacks can remain available to security products at kernel level, provided the relevant drivers are deployed

Important Sysmon EID corrections

  • EID 8 (CreateRemoteThread): QueueUserAPC itself is not what Sysmon EID 8 records; EID 8 specifically records CreateRemoteThread activity. APC injection uses a different API path.
  • EID 10 (ProcessAccess) logs cross-process handle operations with specific access rights. It does NOT log VirtualProtect calls.

Detection opportunities

Correlate the injection sequence across multiple events:

  1. Sysmon EID 1 / Windows Security EID 4688: Process created (check for unexpected parent-child relationships)
  2. EID 10: Cross-process access with suspicious GrantedAccess flags (PROCESS_VM_WRITE, PROCESS_VM_OPERATION)
  3. Correlate process creation with available cross-process access, memory-operation telemetry, and subsequent execution/resumption behavior where the EDR provides those events
title: Suspicious Cross-Process Memory Access Pattern
status: experimental
description: >
    Detects cross-process access with memory write permissions from
    unexpected source processes, which may indicate injection.
logsource:
    category: process_access
    product: windows
detection:
    selection:
        GrantedAccess|contains:
            - '0x1FFFFF'    # PROCESS_ALL_ACCESS
            - '0x1F0FFF'    # PROCESS_ALL_ACCESS (alternate)
    filter_system:

            - 'C:\Windows\System32\'

    This detects suspicious cross-process access patterns. It does NOT
    specifically detect APC injection — correlate with process creation
    and behavioral analysis for higher confidence.
falsepositives:
    - Debuggers
    - Security products
    - Development tools

Defensive controls

  • Use Windows Exploit Protection / process mitigation policies to enable CIG and ACG where compatible
  • Ensure EDR processes run at High integrity level

Technique 08: Process Hollowing and Thread-Context Hijacking

MITRE ATT&CK: T1055.012 (Process Hollowing) for classic hollowing; thread-context hijacking should be mapped according to the specific injection behavior observed
Evidence: Observed in the wild + reproduced in lab

What the attacker does

These are related but technically distinct process-injection techniques:

  • Classic hollowing: Spawns a legitimate process suspended, unmaps the original PE image via ZwUnmapViewOfSection, writes a malicious replacement image, and resumes execution.
  • Thread-context hijacking (RIP hijack): Spawns a process suspended, allocates and writes shellcode into the target, modifies the main thread's instruction pointer (RIP on x64) via GetThreadContext/SetThreadContext to redirect execution. The original image remains mapped.

These techniques share a surface similarity but differ in mechanism and forensic footprint. They should not be treated as interchangeable in detection logic or incident analysis.

TechniqueOriginal imageMain modificationTypical execution redirection
Process hollowingUnmapped/replacedImage replaced in memoryEntry point / redirected execution
Thread-context hijackingRemains mappedShellcode added to targetRIP/EIP modified

What remains visible

  • Sysmon EID 25 (Process Tampering) — can provide a strong signal for process-image tampering. It should not be assumed to detect every hollowing implementation.
  • Sysmon EID 1 — process creation with suspicious parent
  • Memory forensics — in-memory PE headers/sections that don't match the on-disk image (Volatility malfind, hollowfind)

Detection opportunities

  • EID 25 can provide a strong host-level signal for process-image tampering — correlate with EID 1 (process creation) and EID 10 (process access). Detection strength depends on Sysmon configuration and the specific implementation.
  • Memory integrity comparison: running process image vs on-disk file

Defensive controls

  • Enable Sysmon EID 25 (Process Tampering) in your configuration
  • Enable Windows Tamper Protection to prevent attackers from disabling Sysmon
  • Periodic memory integrity snapshots comparing running images to on-disk binaries

Technique 09: Payload Encryption & Environment-Bound Keys

MITRE ATT&CK: T1027 (Obfuscated Files or Information), T1480.001 (Execution Guardrails: Environmental Keying)
Evidence: Observed in the wild + reproduced in lab

What the attacker does

The payload is encrypted using symmetric encryption. The decryption key is derived at runtime from host-specific environmental values such as volume serial, MAC address, or computer name. The required decryption key can only be reproduced when the expected environmental values are present.

What it bypasses

  • Static scanning and signature matching
  • Sandbox dynamic analysis (analysis environments with different host characteristics can fail to reconstruct the expected payload)
  • Static content scanning and application-level inspection of the encrypted payload

What remains visible

  • Entropy analysis — high-entropy sections suggest encryption (triage signal, not standalone)
  • Behavioral pattern — a process that reads system identifiers immediately before performing cryptographic operations
  • Network activity — the decrypted payload must eventually act

Defensive controls

  • Behavioral detection over signature detection — focus on the environment-fingerprinting + crypto + execution sequence
  • Deploy analysis environments that accurately replicate target machine characteristics

Technique 10: Event Log Tampering

MITRE ATT&CK: T1070.001 (Indicator Removal: Clear Windows Event Logs)
Evidence: Observed in the wild + reproduced in lab

What the attacker does

Calls ClearEventLogA/W on System, Application, and Security event log channels. Clearing protected event logs requires appropriate privileges.

What remains visible

  • EID 1102 (Security log cleared) and EID 104 (System/Application log cleared) — ironically, clearing a log generates its own event
  • Events already forwarded to a SIEM
  • Independent endpoint telemetry may reveal the process, privilege escalation, or underlying activity associated with log clearing

Detection opportunities

  • Alert on EID 1102 and EID 104 — EID 1102 should be treated as a high-priority security event because legitimate Security-log clearing is uncommon in many environments
  • Alert on gaps in expected log continuity
  • Monitor for privilege escalation preceding log clearing

Defensive controls

  • Forward logs to SIEM in real-time — this is the single most important control
  • Restrict privileges required for log clearing to the minimum necessary accounts
  • Enable Windows Tamper Protection

Technique 11: PPID Spoofing

MITRE ATT&CK: T1134.004 (Access Token Manipulation: Parent PID Spoofing)
Evidence: Observed in the wild (SideWinder, Lazarus) + reproduced in lab

What the attacker does

Uses UpdateProcThreadAttribute with PROC_THREAD_ATTRIBUTE_PARENT_PROCESS to spawn a process with a forged parent PID. The process-creation metadata can identify a different parent process than the process that actually initiated the creation.

What remains visible

  • Process creation telemetry (Sysmon EID 1, Windows Security EID 4688) still records the event
  • The attacker normally needs access to a suitable existing process handle with the required rights, which constrains which process can be selected as the spoofed parent

Detection opportunities

Do not assume the reported parent PID is necessarily the process that initiated process creation.

Correlate across multiple attributes:

  • Independent creator telemetry vs. reported parent (where available from kernel instrumentation or ETW)
  • Process token and integrity level
  • Command line and image path
  • Handle access patterns (cross-process handle with PROCESS_CREATE_PROCESS)

Detection depends on whether the deployed telemetry architecture records an independent creation context. Without independent creator telemetry, defenders should not assume the true creator can always be recovered.

Technique 12: Fiber-Based Execution

MITRE ATT&CK: Mapping depends on the payload-delivery mechanism; fiber execution itself is better described as an execution/evasion primitive
Evidence: Publicly implemented + behavior reviewed

What the attacker does

Converts the current thread to a fiber (ConvertThreadToFiber), creates a new fiber with the payload as the callback (CreateFiber), and switches to it (SwitchToFiber). The payload executes on the existing thread as a fiber — no new OS thread is created, so NtCreateThreadEx is never called. The term "threadless execution" is sometimes used but is somewhat misleading: execution still occurs on a thread, just without creating a new one.

What it bypasses

  • Thread-creation monitoring (no NtCreateThreadEx, no CreateRemoteThread)
  • Fiber switching does not itself generate Sysmon EID 8 because EID 8 records CreateRemoteThread activity, not fiber operations
  • EDR hooks on thread creation APIs

What remains visible

  • The payload still runs in-process — memory scanning can detect it
  • Any system calls the payload makes are still visible to kernel telemetry, where deployed
  • Network activity from the payload is unaffected

Defensive controls

  • Fiber execution evades thread-creation hooks but not memory or behavioral detection
  • Ensure EDR detection does not rely solely on thread-creation events

What Defenders Can Still Observe After User-Mode Evasion

Every technique above removes one source of telemetry. The defender's job is to correlate the telemetry that remains.

What defenders can observe

1. Process creation — Where kernel callbacks or equivalent independent telemetry are available, process creation remains observable even when user-mode hooks are bypassed.

2. Process access — Where kernel instrumentation is present, cross-process handle operations with suspicious access rights remain observable.

3. Image-load telemetry — Can be collected independently of user-mode ntdll hooks through kernel-supported notification and sensor mechanisms, where available.

4. Process tampering — Sysmon EID 25 can provide a strong signal for image manipulation (hollowing, herpaderping), where Sysmon is deployed and configured.

5. File-system activity — Where MiniFilter drivers are present, file I/O is observable independent of user-mode hooks.

6. Network behavior — For network-controlled malware, C2 communication eventually creates network-observable behavior, although visibility depends on where network telemetry is collected and whether traffic is encrypted, proxied, tunneled, or otherwise obscured.

7. Memory state — For conventional execution, executable instructions must become available in a form the processor can execute, even if only for a short window. Sleep obfuscation narrows the detection window but does not eliminate it.

8. Cross-host correlation — An attacker may evade one endpoint, but lateral movement across multiple endpoints exposes behavioral patterns visible to cloud-based EDR correlation, assuming telemetry reaches the correlation service.

Hardening Checklist

  1. Forward event logs to SIEM in real-time. ClearEventLog only affects the local log. Events successfully received by your SIEM are substantially harder for an endpoint attacker to erase.
  2. Enable Sysmon with a hardened config (SwiftOnSecurity or Olaf Hartong template). A practical starting set: EID 1, 3, 5, 7, 8, 10, 11, 22, 25. Adjust based on environment and telemetry volume.
  3. Baseline ETW telemetry rates per process type. Monitor for statistically significant deviations combined with other suspicious indicators. Missing telemetry is a signal when correlated — not proof of tampering on its own.
  4. Enable kernel-level ETW consumers in your EDR. Ask the vendor which kernel-level telemetry sources they use and whether ETW-TI is part of that telemetry architecture.
  5. Configure sandboxes realistically. 4+ CPUs, 8+ GB RAM, 1080p+ resolution, realistic uptime, installed applications, browser history, user activity simulation.
  6. Use Windows Exploit Protection / process mitigation policies to enable CIG and ACG where compatible. Test before deploying broadly.
  7. Enable periodic memory scanning in your EDR using the shortest practical interval. Sleep obfuscation only works during the sleep window.
  8. Monitor memory protection cycling on private executable regions. Repeated transitions between executable and NOACCESS states warrant investigation, especially with concurrent network beaconing.
  9. Enable CET (hardware stack protection) where hardware supports it (Intel 11th gen+, AMD Zen 3+). Defense-in-depth, not a silver bullet.
  10. Run a purple team exercise against these specific techniques. The only way to know whether your detections fire is to test them.

Common Detection Engineering Mistakes

Writing rules that match a single artifact instead of a behavioral sequence. A rule that fires on VirtualAllocEx alone generates noise. A rule that correlates VirtualAllocEx → cross-process write → thread creation in the target → anomalous network activity within a time window detects the operation, not just the API call.
Assuming telemetry absence means nothing happened. Missing AMSI events from a PowerShell process that is actively executing scripts is itself a signal — but only when correlated with other indicators. Telemetry absence is a triage signal, not proof of tampering on its own.
Treating user-mode hooks as a reliable detection foundation. Every technique in this article demonstrates that user-mode hooks can be bypassed. Kernel telemetry, network visibility, and behavioral correlation provide more durable foundations.
Conflating related techniques in detection logic. Process hollowing and thread-context hijacking share a surface similarity but differ in mechanism and forensic footprint. Write distinct detection logic for distinct techniques.
Testing detections against tool-specific implementations rather than the underlying technique. A Sigma rule tuned to detect a specific Cobalt Strike sleep pattern will miss a custom implant using the same technique with different parameters. Test against the behavioral pattern, not the tool.

What This Article Does Not Claim

This article does not claim that:

  • every EDR collects kernel telemetry;
  • every EDR can detect direct syscalls;
  • ETW-TI is universally available to defenders;
  • Sysmon alone can reconstruct complex injection chains;
  • missing telemetry proves tampering;
  • memory scanning catches every encrypted or injected payload;
  • network telemetry is always available;
  • any individual evasion technique guarantees detection bypass.

Instead, the article argues that defensive visibility improves when independent telemetry sources are correlated rather than treated as interchangeable or universal.

Conclusion

EDR evasion is rarely about becoming invisible. It is about reducing the number of sensors that can see you.

Attackers can patch AMSI. They can interfere with user-mode ETW. They can remove ntdll hooks, invoke syscalls directly, encrypt their memory, spoof process ancestry, or execute without creating conventional threads.

But every technique creates dependencies. The implant still needs CPU execution. It still needs memory. It still needs files, credentials, processes, or system resources. And if it is remotely controlled, it eventually needs a network path.

That gives defenders an important advantage: one telemetry source may be blinded, but multiple independent observations are much harder to erase simultaneously.

The objective of modern detection engineering should not be to build a detection that survives every evasion technique. It should be to build multiple independent detections whose signals converge on the same behavior.

Attackers reduce telemetry. Defenders increase correlation.

That is the cat-and-mouse game.

Blind one sensor, and another should still be watching.
