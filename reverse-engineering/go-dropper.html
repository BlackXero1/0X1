Six Locks, No Key

Reversing a Go dropper's six-step payload decryption, and unpacking its infostealer without ever running it.

TL;DR
  • newGOYAL.exe is a 2.7 MB Go 1.21 dropper from the morganqw ClickFix campaign. It has stripped-looking symbols, no readable strings, and only kernel32 imports.
  • Hidden in .rdata is a 327,984-byte encrypted blob. The dropper decrypts it with six inline byte transforms, not a crypto library.
  • I recovered the function names with GoReSym, found the one function that touches the blob, and read the six loops in disassembly. Then I replayed them in 15 lines of Python.
  • The output was a clean PE64: a novel infostealer that targets Roblox, Steam and Chrome. I never had to execute anything.

The dropper landed as the third stage of a ClickFix chain. It was 2.7 MB, written in Go, and signed with a self-signed certificate for a company called "Sterling Craft Analytics". The first look said almost nothing.

DIE reported Go 1.21.1 with no packer. The import table was kernel32 only: 45 functions, the standard Go runtime set. strings showed Go runtime noise and no URLs, paths or commands. The PE timestamp was zeroed. Nothing on the surface said what this binary was for.

Go malware is popular with operators for this reason. One static binary, a huge runtime that buries your code, and tooling that wasn't built with Go in mind. This post walks through how I got from that blank wall to a decrypted payload, and how you can do the same on the next Go dropper you meet.

01 Why Go binaries feel hard

Opening a Go binary in a disassembler for the first time is disorienting. A few things work against you:

  • The runtime is enormous. A hello-world Go binary contains thousands of functions. Your malware's logic is a few dozen of them.
  • Strings aren't null-terminated. Go stores strings as pointer plus length, packed together in one big blob. Tools that look for C strings split them in odd places or miss them.
  • The calling convention is different. Since Go 1.17, arguments go in registers using Go's own ABI (RAX, RBX, RCX, RDI…), not the Windows x64 convention. Decompilers that assume Windows conventions show garbage parameters.
  • Stripping doesn't really strip. Go keeps a function table, pclntab, for stack traces and garbage collection, so the names are still in there. Tools just need to know how to read it.

That last point is the way in.

02 Step one: get the names back

Before you open a disassembler, run GoReSym. It parses pclntab and the module data, then hands you back function names, source file paths, the Go version, and the build ID.

goresym.exe -t -d -p newGOYAL.exe > goresym.json

That gave me:

Thirty-eight functions in main is a manageable target. Everything else is the Go standard library and can be ignored. The author had randomised the names (main.eNgv2uhCRt, main.w0Ny3IKk), which hides intent but not location. I knew exactly which 38 functions to look at.

Free detection material The module path and build ID survive in every build from this project. SterlingCraftAnalytics also matched the certificate subject. Both went straight into the YARA rule at the end of this post.

03 Step two: find the hidden payload

No readable strings plus runtime API resolution through LoadLibraryW/GetProcAddress usually means something is being decrypted. To find out where, I ran a 16 KB sliding-window entropy scan across the file.

Overall entropy was unremarkable (.text 6.19, .rdata 6.36), which is why DIE said "not packed". The sliding window told a different story. There was a long run above 7.5 inside .rdata, which is what encrypted data looks like. Averaging over the whole section had hidden it.

Next question: which code reads it? Go loads data addresses with RIP-relative LEA instructions. I used capstone to disassemble the 38 main.* functions and resolve every RIP-relative LEA target. Exactly one function pointed into the high-entropy region:

main.eNgv2uhCRt
    lea  rsi, [rip + 0x…]     ; → VA 0x593900  (start of the blob)

One function, one blob, starting at VA 0x593900. The next job was working out what that function does to it.

04 Step three: read the loops

Ghidra struggled here. Two of the main functions were so large that decompilation timed out, and the call into the decryption logic was inlined into a very long body. Instead of fighting the decompiler, I went back to raw disassembly and looked for the shape of a byte-transform loop: a load from [base+i], some arithmetic, a store back to the same address, then inc and cmp against the length.

There were six of these loops back to back, one after another, over the same buffer:

#Loop addressOperationWhat it looks like in asm
10x542a68Rotate each byte left by 4rol al, 4
20x542e8dReverse the whole bufferswap [i] ↔ [0x5012f − i]
30x5432beb = (b + i·0x1D + 0x0B) mod 256imul by 0x1D, add
40x543acbSwap the two halves at 0x28098block copy around midpoint
50x543ee8b = (b − i·17 + 0x51) mod 256imul by 0x11, sub
60x5442f6Rotate each byte left by 4 againrol al, 4

The constants check each other. The reverse loop's upper bound 0x5012f is length − 1, and 0x28098 is exactly length ÷ 2. Both give a blob length of 0x50130 = 327,984 bytes. When two independent constants agree on the size, you know you've read the loops correctly.

Why this is weak crypto, and why that doesn't matter

None of these steps uses a key. A byte rotation by 4 just swaps the two nibbles. Reverse and half-swap only move bytes around. The two linear steps use the byte's own index as the "key". Once you can read the loops, you can undo them, and there's no secret to brute force.

But it was never meant to resist an analyst. It's meant to resist scanners. The blob has no PE header, no repeating patterns and no strings, so a static AV engine or YARA rule sees noise. It only becomes a PE in memory, for a moment, right before it's loaded.

The encryption isn't there to stop you. It's there to stop the signature engine from seeing an MZ header.

05 Step four: replay it in Python

With the six operations known, the decoder is short. I carved the 327,984 bytes from .rdata starting at the file offset for VA 0x593900, then applied the steps in the same order as the binary:

import pefile, hashlib, sys

def rol4(buf):
    return bytearray(((b << 4) | (b >> 4)) & 0xFF for b in buf)

def decrypt(blob):
    b = rol4(blob)                                              # 1  ROL 4
    b.reverse()                                                 # 2  reverse
    b = bytearray((x + i*0x1D + 0x0B) & 0xFF for i, x in enumerate(b))  # 3
    h = len(b) // 2; b = b[h:] + b[:h]                         # 4  half-swap
    b = bytearray((x - i*17 + 0x51) & 0xFF for i, x in enumerate(b))    # 5
    return rol4(b)                                             # 6  ROL 4

pe   = pefile.PE(sys.argv[1])
off  = pe.get_offset_from_rva(0x593900 - pe.OPTIONAL_HEADER.ImageBase)
blob = open(sys.argv[1], "rb").read()[off:off + 0x50130]
out  = decrypt(blob)

assert out[:2] == b"MZ"
open("inner_payload.bin", "wb").write(out)
print(hashlib.sha256(out).hexdigest())

First run:

619adb8364cdeeb2db24d8da5e051e9e4242033f6fb1931e90e42116609a8fad

The MZ assert passed, and pefile parsed the output as a valid PE64 with .text, .rdata, .data and .reloc. Its compile timestamp was 2026-11-06, four days before the campaign's delivery timestamp. The dropper was unpacked, and I hadn't executed a single instruction of it.

Why a static replay beats dumping from memory here The next stage turned out to have anti-sandbox checks, and every detonation in my VM exited within five seconds. A memory-dump approach would have got nothing. A static replay doesn't care what the malware thinks of your VM.

06 What came out

inner_payload.bin is a C/C++ PE64 with zero YARA matches across 1,062 community rules. It's a custom infostealer. It also encrypts its strings at rest, but FLOSS decoded them, and its import table already gave away a lot:

It also has three gates in its entry point. One of them walks the PEB module list, hashes every loaded DLL name, and quits silently if any of 18 hashes match. That explains the five-second exits during detonation. The full payload analysis is in the ClickFix post; this one is about getting to it.

07 The method, for your next Go dropper

  1. GoReSym first. Get the names, the version and the module path before opening a disassembler. Filter to main.* and ignore the runtime.
  2. Use sliding-window entropy, not section entropy. Averages hide embedded blobs.
  3. Follow the RIP-relative LEAs. Find which main function references the high-entropy range. That's usually your decryptor.
  4. When the decompiler times out, read loops. Load, arithmetic, store, increment, compare. Byte-transform loops are easy to spot in raw assembly.
  5. Make the constants check each other. Lengths, midpoints and loop bounds should agree. If they don't, you've misread something.
  6. Replay in Python and assert on the output. MZ at offset 0 and a clean pefile parse are your proof.

08 Detection

The dropper leaves stable features that don't depend on the payload:

rule morganqw_go_dropper {
    meta:
        description = "Go dropper from morganqw ClickFix chain (newGOYAL.exe)"
        author      = "BlackXero1"
        date        = "2026-11-20"
        hash        = "0888ba835230f7675117e263ecac24a9c8443172780ce0b31f22a9ff938e9d62"
    strings:
        $go     = "Go build ID:" ascii
        $mod    = "SterlingCraftAnalytics" ascii
        $bid    = "9IvKqeaCdMt8sElOh9GO/" ascii
        $rol4   = { C0 C0 04 }                // rol al, 4
    condition:
        uint16(0) == 0x5A4D and $go and ($mod or $bid) and #rol4 >= 2
}

Detection beyond YARA:

  • Certificate: self-signed, subject "Sterling Craft Analytics", thumbprint 9099B4EC70C56DFD23B20814D47EB3E3AEB92405. Hunt for siblings signed with the same certificate.
  • Behaviour: an unsigned or self-signed Go binary launched from a %TEMP%\<guid>\ folder by powershell.exe, which then allocates executable memory.

09 Takeaways

The short version

Go isn't obfuscation; it's just unfamiliar. Recover the symbols, narrow down to main, find the function that touches the high-entropy data, and read its loops. Homemade "encryption" built from rotates and index-based arithmetic is reversible as soon as you've read it.

What I didn't get: the dropper's exact loading path for the decrypted PE wasn't fully traced. The large main functions defeated the decompiler, and imports of VirtualAlloc and ResumeThread suggest in-memory loading, but I haven't confirmed which technique it uses. That's an open question for anyone who picks up this sample next.
